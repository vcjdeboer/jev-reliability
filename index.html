Ask It Again

How repeatable is Jev? We asked it the same question 1,252 times and split up what moved the answer.

Written by Claude Opus 5, on behalf of Vincent de Boer · September 2026

Where this started

We read an article on dev.to about putting Jev behind a TLA+ specification and running 1,680 pharmacy decisions through it under chaos testing.2 One line in it stuck with us: the same request, sent five times, came back 0.03, 0.03, 0.03, 0.04, 0.04.

So the model does not always give the same answer to the same question. We wanted to know how much that matters, and what else moves the answer besides chance. We set up some tests.

What Jev is

Jev doesn't write text. It belongs to a different category — judgment models, or System One models — and gives back a number instead of prose.1

Ask it does this customer sound angry? and you get 0.9. Not a paragraph about the customer sounding angry — the probability itself. It is trained for calibrated decisions rather than for replies people like, and it answers in three shapes: a yes/no probability, a choice among options you define, or a score across ordered levels.

That makes it something code can use directly. A chat model asked the same thing replies "You're absolutely right, this customer does sound very angry — shall I draft a response?", which breaks a program expecting a number. Jev fits where software branches on a judgment: route this, escalate that, hold this one back.

How we split up the movement

Asking the same question repeatedly tells you the answer wobbles. It doesn't tell you why. Two calls can differ in three ways, and we wanted each one separately:

What differs between two callsExample
nothing at allthe identical request, sent again
something that can't mattertrailing whitespace, or an extra field nothing reads
the wordingthe same question asked a different way

On top of that, different texts genuinely differ from each other, and that is the part you actually want the model to pick up.

We fitted a Bayesian multilevel model to pull those four apart. The idea is simple enough: every answer is treated as the sum of a few contributions — this text, this wording, this particular call — and the model works backwards from 1,252 answers to estimate how big each contribution is. Because it's Bayesian, each estimate comes out as a range rather than a single number, which is what lets us say whether two of them are really different or only look different.

We wrote the design down and committed it before collecting anything, along with what we expected and what would count as being wrong. Every later change is logged as a numbered deviation.

What came out

It repeats itself, except in the middle

Sending byte-identical requests twenty times, texts at either end of the scale came back with the same answer every time. Texts in the middle came back with up to sixteen different answers in twenty calls.

We had nearly used only clear-cut examples. That would have shown perfect repeatability and told us nothing.

Three sizes of movement

What changed between callsmovement (sd, 0–3 scale)
nothing0.0102
something that can't matter0.0204
the wording0.0347

Rewording moves the answer most. The middle row is the one we didn't expect — adding a field nothing reads moves the answer about twice as much as just asking again.

A lot of texts get exactly the same number

Of thirty texts, thirteen came back with exactly identical values: six at the bottom of the scale, seven at the top. Sort that list and the order inside those two blocks is arbitrary. Allowing for noise, 17% of all pairs were too close to separate.

A threshold can flip without anything changing

One text came back with confidence between 0.46 and 0.53 across repeated identical requests. A gate written confidence >= 0.5 lands on both sides of that across runs.

The answer itself held up better — the top choice almost never moved. On a yes/no question we measured how often the decision changed:

ConditionDecisions that change
same request, repeated0.0%
question reworded12.5%

It rates things that have nothing to rate

We asked how formal the single word yes is. The model came back 98% confident that it was maximally casual writing. We then asked a second question alongside it — is there enough here to judge at all? — and got 2%.

Over twenty texts, half of them real prose and half not writing at all (a bare number, a URL, a base64 blob), the second question separated them completely and confidence did not. A list of mathematical constants came back rated more formal than a release note.

Things we got wrong

One of our controls wasn't a control. The change that was supposed to reorder the fields of a request sorted them and then reversed them, which for a two-field object gives back the original order. It was byte-identical to changing nothing, for a whole run of 480 calls. We had read that code several times. We found it only after the tool started hashing every request and comparing them.

Fixing it more than doubled the measured movement from changes-that-can't-matter, and flipped a conclusion — we had said those changes were indistinguishable from asking again, and they aren't.

We predicted the wrong direction. We expected that loading the test with hard, middle-of-the-scale texts would make our reliability number cautious. The easy texts dominate it instead, so it comes out flattering.

We suggested adding up repeated calls as if they were repeated experiments. They aren't. It's one opinion sampled over and over, and averaging it gives you a very precise estimate of the model's opinion and nothing about whether the opinion is right.

Our model was the wrong shape. We had assumed every text is equally sensitive to rewording. It never fit the data, because two texts out of fourteen are far more sensitive than the rest. Allowing for that fixed the fit — and the rewording effect we'd called real became consistent with zero.

AssumptionFitsRewording effect
all texts equally sensitiveno0.0022 [0.0007, 0.0041]
a few far more sensitiveyes0.0004 [0.0000, 0.0011]

So rewording is not harmless, but the risk sits in a few questions rather than being spread across all of them. One average number doesn't describe it.

Published noise floors for the same model version come out in the same order — repeating, then changing something irrelevant, then rewording — at a ratio of 1.74 against our 1.70.2 Our data before the fix did not match that, because the broken control had merged two of the three.

What we can't say

Nothing about accuracy. All of this is about whether the model is consistent, not whether it's right. Checking that needs labelled examples, which is a different job. It's also one model version, a handful of questions and a few dozen texts.

The tests, as a tool

We packaged the checks as a swamp extension so we could point them at the next question instead of rebuilding them.

swamp extension pull @vcjdeboer/jev-reliability

swamp model method run @vcjdeboer/jev-reliability check myquestion \
  --input-file myquestion.json

swamp report get @vcjdeboer/jev-reliability-report --model myquestion

It reports how often the decision changes, which items are tied, whether a threshold is stable, whether the text supports an answer at all, and where the movement comes from. It hashes every request and won't count a change that produced an identical one — that's what caught our broken control. If the model fit hasn't converged it says so instead of printing the numbers.

The code, the raw data, the preregistration and the deviations are in the repository.3
