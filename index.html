Measuring the Instrument

A judgment model is sold as something you can put behind an if. So we measured what happens to the if.

Vincent de Boer · September 2026

Summary

We ran 1,252 calls against a single pinned version of Jev, to a design fixed in advance, and treated it as an instrument to be characterised, the way you would characterise a plate reader before trusting a plate.

It is not deterministic, but only where the answer is genuinely uncertain. Rewording a question moves the answer more than random noise does. The scale saturates, so a large fraction of any corpus cannot be ranked at all. A fixed threshold can flip on byte-identical input. And the model will confidently rate text that has nothing to rate — which its own confidence score cannot detect, and a second question can.

It also caught three errors in our own study, one of which had survived repeated code review, and the model that finally fit the data dissolved a result we had already published to ourselves.

What Jev is

Most of what the last four years called "AI" writes text. Jev does not. It belongs to a different category — judgment models, or what its makers call System One models — and instead of prose it returns a number.1

Ask it does this customer sound angry? and you get 0.9. Not a paragraph explaining that the customer sounds angry: the probability itself. Where an ordinary language model is trained to produce responses people prefer, this one is trained to produce calibrated decisions — probabilities meant to be honest about their own uncertainty.

That single property is the whole point, because it makes the output something code can consume. A chat model handed the same question replies "You're absolutely right, this customer does sound very angry — would you like me to draft a response?", which crashes a program expecting a number between zero and one. Three shapes are available: a yes/no probability, a choice among options you define, and a score across ordered levels.

The practical framing that has stuck is that most software is a large tree of if this, do that — route here, escalate that, reject the other — and a judgment model lets those branches read messy human context instead of fixed rules. It is fast and cheap enough to sit inside the branch rather than beside it: hundreds of judgments in under a second, for a fraction of a cent.

Which is exactly why it is worth measuring. A number you merely read is one thing. A number you put behind an if is a different thing, because now its wobble becomes your program's behaviour.

Why measure at all

Two people have already built serious systems on Jev and published what they found. One put it behind a TLA+ specification and ran 1,680 chaos-tested pharmacy decisions, reporting no confidently wrong verdicts and measuring the model's noise floor across 1,490 captured calls.2 Another put it in front of an on-call alert queue as a cheap screen before an expensive model, reporting roughly 99.9% lower screening cost.3

Both did their own measurement, by hand, and both hit the same wall from opposite directions — a stability gate can detect that a value is jittering, but not that no value is warranted at all.

The vendor documentation says to validate performance in your target domain. It does not say how. The published cookbooks pick thresholds by assertion. So the gap is not that nobody is measuring; it is that everybody is measuring privately, once, and throwing the apparatus away.

Method: a plate reader for text

There is an existing framework for exactly this problem, and it comes from mitochondrial physiology. OCRbayes models oxygen consumption measurements as a quantity observed with noise at three nested levels — repeated reads of one well, replicate wells on a plate, replicate plates — and estimates how much variation each level contributes.4

A Jev call maps onto that structure directly. One call is one assay:

Assay facetJev equivalent
repeated reads of one wellrepeat calls, byte-identical request
replicate wells on a platea change that cannot alter a correct answer
replicate platesthe item being judged

The middle level is where the design does its work, and it is deliberately split in two. Null perturbations are changes that cannot alter a correct answer: trailing whitespace, reordering keys in the request body, adding an irrelevant field. Variance there is unambiguously instrument noise. Paraphrases are rewordings intended to ask the same question. Variance there is noise plus any drift in what is actually being asked.

Two wells on a plate measure the same quantity. Two phrasings of a question might not. Keeping them apart, and never pooling them, is what lets their contrast separate "the instrument is noisy" from "you changed the question".

The design, the predicted outcomes, and the conditions that would count as falsification were written down and committed to version control before any data was collected. Every later change is recorded as a numbered deviation, including the ones that went against us. That discipline is the only reason the errors described below are legible rather than invisible.

What we found

It is not deterministic — but only in the middle

Sending byte-identical request bodies twenty times, items at the extremes of the scale returned one identical distribution every time. Items in the middle returned up to sixteen different distributions in twenty calls.

This is the finding that nearly escaped. Had the test used only clear-cut examples — the obvious thing to do — it would have concluded the model was deterministic and been wrong. Determinism at saturation is trivially satisfied; the sensitive test is where the answer is genuinely uncertain, which is also the only place the answer is interesting.

Three tiers of variation

Across 480 calls over thirty items, eight framings and two repeats:

Source of variationsd (0–3 scale)
repeating the identical request0.0102
a semantically null perturbation0.0204
rewording the question0.0347

Two things follow. Rewording moves the answer most — the phrasing of your question is part of your measurement, and should be versioned like code. But also: a null perturbation is not free. Adding an irrelevant field to a request moves the answer about twice as much as simply asking again does. Nothing in the request is inert.

The scale saturates, so much of a corpus cannot be ranked

Of thirty items, thirteen returned exactly identical values — six pinned at the floor, seven at the ceiling. Within those groups there is no ordering to recover. Accounting for noise, 17.0% of all item pairs were statistically indistinguishable.

A ranking built on this would present a confident, complete ordering in which roughly one pair in six is a coin flip, and two large blocks are arbitrary.

A fixed threshold can flip on identical input

One item returned confidence ranging from 0.46 to 0.53 across repeated byte-identical requests. Any gate written confidence >= 0.5 flips between runs with nothing whatsoever changed.

The decision itself is more robust than the number: across every study the modal answer almost never moved. It is the threshold, not the judgment, that is fragile — which matters, because thresholds are how these models get wired into software.

On a gate-shaped question we measured this directly as a flip rate:

ConditionDecisions that change
same request, repeated0.0%
question reworded12.5%

It will confidently rate things that have nothing to rate

Asked how formal the single word yes is, the model answered with 98% confidence that it was maximally casual writing. Asked a second, separate question — is there actually enough here to judge? — it answered 2%.

Across twenty items split between real prose and things that are not writing at all (a bare number, a URL, a base64 blob), the answerability question separated the two classes perfectly; confidence did not. It fails in both directions: a list of mathematical constants was rated more formal than a release note, while genuine prose drew low confidence and would have been escalated for no reason.

These are different questions. Confidence asks is the level determined? Answerability asks is there anything to level? A stability gate structurally cannot detect the second, which is the wall both earlier projects hit.

What we got wrong

Four errors, kept here because they are the most useful part of the study.

A control that was not a control. One "null perturbation" reordered the keys of the request body — except that the transform sorted the keys and then reversed them, which for a two-field object returns the original order. It was byte-identical to the control, for the entire collection. It survived several careful readings. It was caught only when the tool began hashing every request body and comparing, at which point it was obvious and instant.

Fixing it more than doubled the measured noise from null perturbations, and reversed a published conclusion: we had reported that null changes were indistinguishable from simply repeating a call. They are not.

A prediction that came out backwards. We argued in advance that over-sampling hard, mid-scale items would make the reliability estimate conservative. The opposite happened — the saturated items dominate the between-item variance and make reliability look better than it is.

A recommendation that was simply wrong. Early on, reasoning from the assay analogy, we proposed accumulating evidence across repeated calls the way a lab accumulates independent assays. Repeated calls are not independent assays. They are one opinion sampled repeatedly, and pooling them would have manufactured precision about the model's opinion while saying nothing about the truth. The pharmacy project reached the same conclusion from its own data: five agents on one prompt are one agent.2

A result that dissolved under a better model. The variance model assumed every item is equally sensitive to rewording. It failed its own predictive check in every collection, because two of fourteen items are far more sensitive than the rest. Refitting with a heavy-tailed model fixed the fit — and the difference between paraphrase and null variance, which the first model declared established, became consistent with zero.

ModelPredictive checkParaphrase drift
equal sensitivityfails0.0022 [0.0007, 0.0041]
heavy-tailedpasses0.0004 [0.0000, 0.0011]

The honest reading is not that rewording is harmless. It is that the risk is concentrated rather than uniform: most questions barely move under rewording, and a minority move a great deal. Which means no single "noise floor" number describes it — the average is not a typical value, and the tail is what reaches production.

Where this agrees with others

The pharmacy project measured three noise floors on the same model version and found them ordered: repeating a request < reordering a question < paraphrasing it.2 Our corrected data reproduces that ordering and lands at a paraphrase-to-perturbation ratio of 1.70 against their 1.74 — two different designs, different questions, the same structure.

Notably, our uncorrected data did not reproduce it: the broken control had collapsed two of the three tiers into one. The external comparison would have caught the bug even if our own tooling had not.

What this cannot tell you

Nothing about accuracy. Every measurement here is about whether the model is consistent, never whether it is right. A perfectly repeatable question can be repeatably wrong, and this design could not tell. The pharmacy project did test correctness against labels; that is a different study and a necessary one.

Everything is one model version, a small number of questions, and a few dozen items. The specific numbers do not transfer. The method does.

The apparatus

The measurements are a swamp extension, so the apparatus outlives the study rather than being thrown away with it. You give it a question and some items; it returns a verdict on whether that question is safe to build on.

swamp extension pull @vcjdeboer/jev-reliability

swamp model method run @vcjdeboer/jev-reliability check myquestion \
  --input-file myquestion.json

swamp report get @vcjdeboer/jev-reliability-report --model myquestion

It reports the decision flip rate, the tie structure, threshold stability, answerability, and a nested variance decomposition — and it refuses to print the posterior when the fit has not converged, rather than printing numbers you should not read. It does not take your paraphrases on trust: it hashes every request body and declines to count a perturbation that produced an identical request. That check is what found the broken control above.

The code, the raw data from every study, the preregistration and all deviations are in the repository.
