Ask It Again

A judgment model gives you a number you can put behind an if. So we asked it the same question twice.

Written by Claude Opus 5, on behalf of Vincent de Boer · September 2026

Summary

1,252 calls to one pinned version of Jev, to a design fixed in advance.

Asked the identical question twice, it usually — but not always — gives the identical answer. Rewording the question moves the answer more than repeating it does. Many texts come back with exactly the same number, so they cannot be ranked against each other at all. A fixed threshold can flip on byte-identical input. And it will confidently rate text that has nothing to rate — which its own confidence score cannot detect, and a second question can.

The study also made three errors. One survived repeated code review, and the model that finally fit the data dissolved a result we had already convinced ourselves of.

What Jev is

Most of what gets called AI writes text. Jev does not. It belongs to a different category — judgment models, or System One models — and returns a number instead of prose.1

Ask it does this customer sound angry? and the answer is 0.9. Not a paragraph saying the customer sounds angry: the probability itself. Where a language model is trained to produce responses people prefer, this one is trained for calibrated decisions — probabilities meant to be honest about their own uncertainty. Three shapes are available: a yes/no probability, a choice among options you define, and a score across ordered levels.

That is the whole point, because it makes the output something code can consume. A chat model handed the same question replies "You're absolutely right, this customer does sound very angry — shall I draft a response?", which crashes a program expecting a number. Most software is a large tree of if this, do that, and a judgment model lets those branches read messy human context instead of fixed rules — cheap and fast enough to sit inside the branch rather than beside it.

Which is why it is worth checking. A number you read is one thing. A number behind an if is another, because its wobble becomes your program's behaviour.

Why check

Published work already reports noise floors, chaos-tested decision systems and cost comparisons.23 What none of it leaves behind is the apparatus — the checking gets done once, by hand, and thrown away with the project.

The vendor documentation says to validate performance in your own domain. It does not say how, and the published recipes pick their thresholds by assertion.

Method

The design comes down to asking the same thing several ways and seeing what moves the answer. Three things can differ between two calls:

What changesExample
nothingthe identical request, sent again
something that cannot mattertrailing whitespace; an unused extra field
the wordingthe same question asked differently

Keeping the middle row separate from the bottom one is what the whole design turns on. Adding whitespace cannot change the right answer, so anything that moves is noise from the model. Rewording is meant to ask the same question, but it might quietly ask a slightly different one — so movement there is noise plus whatever the rewording changed. Pooling the two would make those indistinguishable.

Each of the three is repeated many times across many texts, so the movement can be attributed rather than just observed: how much comes from the model repeating itself, how much from a change that should not matter, how much from the wording, and how much is simply one text differing from another. Those four are estimated together, so that an effect at one level cannot be quietly credited to a different one.

The design, its predicted outcomes and the conditions that would count as failure were committed to version control before any data was collected. Every later change is a numbered deviation, including the ones that went the wrong way.

What we found

Not deterministic — but only in the middle

Sending byte-identical requests twenty times, texts at the extremes of the scale came back with one identical answer every time. Texts in the middle came back with up to sixteen different answers in twenty calls.

This nearly escaped. A check using only clear-cut examples — the obvious thing to build — would have concluded the model was deterministic and been wrong. Where the answer is obvious, agreement is free. The sensitive case is where the answer is genuinely uncertain, which is the only place it is interesting.

Three tiers of movement

What changed between callsmovement (sd, 0–3 scale)
nothing0.0102
something that cannot matter0.0204
the wording0.0347

Rewording moves the answer most: the phrasing of a question is part of the measurement, and should be versioned like code. But the middle row is the surprise — adding an irrelevant field to a request moves the answer about twice as much as simply asking again. Nothing in the request is inert.

Many texts get exactly the same number

Of thirty texts, thirteen came back with exactly identical values — six at the bottom of the scale, seven at the top. Within those two blocks there is no order to recover. Allowing for noise, 17% of all pairs were indistinguishable.

Sort that list and you get a confident, complete ranking in which roughly one pair in six is a coin flip.

A fixed threshold can flip on identical input

One text came back with confidence between 0.46 and 0.53 across repeated byte-identical requests. Any gate written confidence >= 0.5 flips between runs with nothing changed.

The decision holds up better than the number — the top answer almost never moved. It is the threshold that is fragile, which matters, because thresholds are how these models get wired into software. On a yes/no question, measured directly:

ConditionDecisions that change
same request, repeated0.0%
question reworded12.5%

It will confidently rate things that have nothing to rate

Asked how formal the single word yes is, the model answered with 98% confidence that it was maximally casual writing. Asked a separate question — is there enough here to judge at all? — it answered 2%.

Across twenty texts split between real prose and things that are not writing (a bare number, a URL, a base64 blob), that second question separated them perfectly and confidence did not. It fails in both directions: a list of mathematical constants was rated more formal than a release note, while ordinary prose drew low confidence and would have been escalated for nothing.

The two questions are not the same. Confidence asks is the level settled? Answerability asks is there anything to settle? Watching a number for stability cannot tell you the second, which is the wall published work keeps reaching.

What we got wrong

A control that was not a control. One of the changes-that-cannot- matter reordered the fields of the request — except the code sorted them and then reversed them, which for a two-field object gives back the original order. It was byte-identical to doing nothing, for an entire run of 480 calls, and it survived several careful readings. It was caught only once the tool started hashing every request and comparing.

Fixing it more than doubled the measured noise from changes-that-cannot-matter, and reversed a conclusion: we had reported that such changes were indistinguishable from simply asking again. They are not.

A prediction that came out backwards. We argued in advance that loading the test with hard, middle-of-the-scale texts would make the reliability estimate cautious. The easy texts dominate instead, which makes reliability look better than it is.

A recommendation that was simply wrong. We proposed adding up evidence across repeated calls, the way repeated experiments are combined. Repeated calls are not repeated experiments. They are one opinion sampled over and over, and adding them up manufactures precision about the model's opinion while saying nothing about the truth.

A result that dissolved under a better model. The analysis assumed every text is equally sensitive to rewording. It failed its own check every time, because two texts out of fourteen are far more sensitive than the rest. Allowing for that fixed the fit — and the rewording effect it had declared real became consistent with zero.

AssumptionFits the dataRewording effect
all texts equally sensitiveno0.0022 [0.0007, 0.0041]
a few far more sensitiveyes0.0004 [0.0000, 0.0011]

The honest reading is not that rewording is harmless, but that the risk is concentrated rather than spread out: most questions barely move, a few move a great deal. No single "noise floor" number describes that. The average is not a typical case, and it is the rare sensitive one that reaches production.

Published noise floors for the same model version come out ordered the same way — repeating < changing something irrelevant < rewording — at a ratio of 1.74 against 1.70 here.2 The uncorrected data did not reproduce that ordering, because the broken control had collapsed two tiers into one. Comparing against outside numbers would have caught the bug even if the tooling had not.

What this cannot tell you

Nothing about accuracy. All of it is about whether the model is consistent, never whether it is right. A perfectly repeatable answer can be repeatably wrong, and this design could not tell. Testing correctness needs labelled examples and is a separate job.

This is one model version, a handful of questions, a few dozen texts. The numbers do not transfer. The method does.

The apparatus

The checks are a swamp extension, so they outlive the study. Give it a question and some examples; it tells you whether that question is safe to build on.

swamp extension pull @vcjdeboer/jev-reliability

swamp model method run @vcjdeboer/jev-reliability check myquestion \
  --input-file myquestion.json

swamp report get @vcjdeboer/jev-reliability-report --model myquestion

It reports how often the decision changes, which items are tied, whether your threshold is stable, whether the text supports an answer at all, and where the movement comes from — and it refuses to print the model fit when that fit has not converged, rather than printing numbers nobody should read. It does not take your rewordings on trust either: it hashes every request and declines to count a change that produced an identical one. That check found the broken control above.

The code, the raw data, the preregistration and every deviation are in the repository.
