Ask It Again

Jev doesn't always give the same answer to the same question. We ran 1,252 calls to find out what actually moves it, and packaged the tests as a swamp extension so they can be pointed at any question.

Written by Claude Opus 5, on behalf of Vincent de Boer · September 2026

Where this started

We read an article on dev.to about putting Jev behind a TLA+ specification and running 1,680 pharmacy decisions through it under chaos testing.2 TLA+ is a language for writing down precisely how a system is allowed to behave, so a checker can walk every reachable state and find the ones that break your rules — a proof that the design holds, before any code exists.

One line in the article stuck with us: the same request, sent five times, came back 0.03, 0.03, 0.03, 0.04, 0.04.

So the model doesn't always give the same answer to the same question. We wanted to know how much that matters, and what else moves the answer besides chance.

What Jev is

Jev, from TypeSafe, doesn't write text. It belongs to a different category — judgment models, or System One models — and gives back a number instead of prose.1

Ask it does this customer sound angry? and you get 0.9. Not a paragraph about the customer sounding angry — the probability itself. It is trained for calibrated decisions rather than for replies people like, and it answers in three shapes: a yes/no probability, a choice among options you define, or a score across ordered levels.

That makes it something code can use directly. A chat model asked the same thing replies "You're absolutely right, this customer does sound very angry — shall I draft a response?", which breaks a program expecting a number. Jev fits where software branches on a judgment: route this, escalate that, hold this one back.

What we did

The question we studied came from jev-voice, an extension we'd already built on Jev. It profiles a piece of writing along six dimensions — formality, authority, complexity, warmth, pace and conviction — and for each one returns not a label but the full spread across the levels, so a text that sits 60% formal and 40% conversational is reported as exactly that rather than rounded to the nearest verdict. Having shipped it, we wanted to know how much those numbers could be trusted.

So we took one of its six questions — how formal is this writing?, answered on a four-level scale — and wrote thirty short texts to ask it about. Eight obviously casual, eight obviously formal, and fourteen deliberately in between, the kind where two people would reasonably disagree.

Then we asked Jev about every text under eight different versions of the same request, twice each. Four of those versions changed something that cannot change the right answer — trailing whitespace on the instructions, an extra field in the request that nothing reads, the fields in a different order. The other four reworded the question itself, keeping the meaning but changing the sentences.

That gives four things that can differ between any two calls:

What differsExample
nothing at allthe identical request, sent again
something that can't mattertrailing whitespace; an unused extra field
the wordingthe same question asked a different way
the text being judgeda chat message versus a legal clause

The last one is the signal — it's what you're paying the model to notice. The first three are all ways of being wrong.

Alongside that we ran two smaller sets: a yes/no gate question (does this message need a human today?) on eight messages, to see what happens to an actual decision rather than a score; and twenty texts where half weren't writing at all — a bare number, a URL, a base64 blob — to see what the model does when there is nothing to judge.

1,252 calls in total, all against one pinned model version, so an update mid-study couldn't be mistaken for noise.

Pulling the numbers apart

Repeating a question tells you the answer wobbles. It doesn't tell you which of those four things caused the wobble, because in the raw data they're all tangled together.

So we fitted a multilevel model. The idea is that every answer is the sum of a few hidden contributions — one for this text, one for this wording, one for this particular call — and if you have enough answers you can work backwards and estimate how big each contribution is. Fourteen texts times eight wordings times two repeats gives enough overlap to separate them.

We did it the Bayesian way, which mainly means the answer comes out as a range instead of a single number. Rather than "rewording contributes 0.035", you get "somewhere between 0.016 and 0.036, most likely around 0.025". That matters here, because the whole question is whether one contribution is genuinely bigger than another, and two ranges that overlap heavily aren't telling you that.

We also checked the model against itself, which is worth explaining because it's what changed our conclusion. Once fitted, a model can generate fake data. If that fake data doesn't look like the real data, the model is wrong about something, however confident its numbers look. We ran that check every time.

What came out

It repeats itself, except in the middle

Sending byte-identical requests twenty times, the obviously-casual and obviously-formal texts came back with the same answer every time. The in-between texts came back with up to sixteen different answers in twenty calls.

Had we used only clear-cut examples, we'd have measured perfect repeatability and learned nothing.

Three sizes of movement

What changed between callsmovement (sd, 0–3 scale)
nothing0.0102

Rewording moves the answer most. The middle row is the one we didn't expect: adding a field nothing reads moves the answer about twice as much as just asking again.

A lot of texts get exactly the same number

Of the thirty texts, thirteen came back with exactly identical values — six at the bottom of the scale, seven at the top. Sort that list and the order within those two blocks is arbitrary. Allowing for noise, 17% of all pairs were too close to separate.

A threshold can flip without anything changing

One text came back with confidence between 0.46 and 0.53 across repeated identical requests. A gate written confidence >= 0.5 lands on both sides of that from one run to the next.

The answer itself held up better — the top choice almost never moved. On the yes/no gate we measured how often the decision changed:

ConditionDecisions that change
same request, repeated0.0%
question reworded12.5%

It rates things that have nothing to rate

We asked how formal the single word yes is. The model came back 98% confident that it was maximally casual writing. We then asked a second question in the same request — is there enough here to judge at all? — and got 2%.

Across the twenty mixed texts, that second question separated real prose from non-writing completely, and confidence did not. A list of mathematical constants came back rated more formal than a release note.

Where it ended up

Our first model assumed every text reacts to rewording by roughly the same amount. On that assumption, rewording clearly mattered more than the changes that can't matter, and we were ready to say so.

Then the self-check failed. Fake data generated from the fitted model was consistently more spread out than the real data — the model expected typical texts to move around more than they actually did.

The reason turned out to be that the assumption was wrong. Two of the fourteen in-between texts are far more sensitive to rewording than the other twelve: their answers move by around 0.37 where the rest move by 0.09. Forced to use one number for everyone, the model split the difference, and overstated the typical case to accommodate the two extremes.

So we refitted allowing a few texts to be much more sensitive than the rest — a Student-t shape rather than a bell curve. A bell curve says extremes are rare; a Student-t says most things sit near the middle but genuine outliers turn up far more often than a bell curve would allow. That version passed the self-check.

AssumptionPasses self-checkRewording effect
all texts equally sensitiveno0.0022 [0.0007, 0.0041]
a few far more sensitiveyes0.0004 [0.0000, 0.0011]

Under the model that fits, the range for the rewording effect reaches down to zero. So the conclusion we'd been heading for — rewording a question systematically moves Jev's answers — doesn't survive. For most texts, rewording does about as much as adding a stray whitespace character.

What replaces it is more useful. Rewording isn't a general tax on accuracy, it's a property of specific questions and specific inputs. A handful are very sensitive; the rest barely notice. That means an average "noise floor" for a model is the wrong thing to ask for — the number you want is which of your questions are the fragile ones. Two out of fourteen, here, and you cannot tell which by reading them.

For what it's worth, published noise floors for the same model version come out in the same order we measured — repeating, then changing something irrelevant, then rewording — at a ratio of 1.74 against our 1.70.2

None of this says anything about whether Jev is right. Everything here is about whether it's consistent. That's a separate question and it needs labelled examples.

The tests, as a tool

We packaged the whole thing as a swamp extension, so it can be pointed at the next question instead of rebuilt.

swamp extension pull @vcjdeboer/jev-reliability

swamp model method run @vcjdeboer/jev-reliability check myquestion \
  --input-file myquestion.json

swamp report get @vcjdeboer/jev-reliability-report --model myquestion

You give it a question and some examples. It tells you how often the decision changes, which items came back tied, whether your threshold sits somewhere unstable, whether the text supports an answer at all, and which of the four sources the movement is coming from. If the model fit hasn't settled, it says so instead of printing numbers.

It also hashes every request and refuses to count two that turned out identical. That check earned itself immediately: one of our supposed changes-that-can't-matter was reordering two fields that were already in that order, so for 480 calls it was secretly just asking the same question again. We'd read the code several times without seeing it.

The code, the raw data and the full write-up are in the repository.3
